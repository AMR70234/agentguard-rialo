HOW AGENTGUARD PROTECTS EVERY JOB

Security, layer by layer

AgentGuard doesn't rely on one safeguard. Every job passes through six independent layers — access control, execution review, on-chain settlement, dispute resolution, automatic timeout handling, and result integrity checks — so no single point of failure controls the outcome.

The six layers

Latch-scoped access

The agent never holds a raw OpenAI or Circle API key. Every action — AI processing, USDC transfers, and smart contract execution — is routed through an independently-scoped Latch policy that enforces endpoint allowlists, rate limits, and spend caps before the request ever reaches OpenAI or Circle.

AgentGuard (OpenAI)/v1/chat/completions60 req/min, $5/day, gpt-4o-mini / gpt-4o only

Independent verification

The worker executes each task with one model. A separate model reviews the result before any funds move — so no model grades its own work. Confidently-stated facts about anything time-sensitive are rejected unless they carry an explicit outdated-information caveat.

On-chain escrow

Funds are held by a smart contract deployed on Arc Testnet, not by this application server. Built on OpenZeppelin's audited primitives with reentrancy protection, and a safety valve: if a dispute sits unresolved for 7 days, anyone can trigger a refund to the client.

AI arbitration with majority voting

A disputed job is reviewed by two genuinely different models — two double-weighted votes from gpt-4o and one independent vote from gpt-4o-mini — not one model called three times. The majority verdict decides release or refund. A rare tie routes to a password-protected admin dashboard for manual review, and a keeper network automatically force-refunds jobs stuck in that queue past a safety threshold.

Emergency pause

The contract inherits OpenZeppelin's Pausable. If a critical bug were ever found, the contract owner can immediately block new jobs and releases without redeploying — existing disputes can still be arbitrated or force-refunded even while paused, so escrowed funds are never permanently frozen.

Keeper network

Jobs stuck in manual arbitration aren't left waiting on a human indefinitely. A lightweight keeper sweeps periodically and calls the contract's forceRefund() automatically once a job has been stuck past a safety threshold — real onchain automation for the unhappy path, not just the happy one.

Commit-Reveal integrity

The worker's result is hashed the instant it's produced, before it's shown to anyone. A second hash computed at reveal time is compared against the commit — cryptographic proof the exposed result wasn't swapped or tampered with between execution and display.

Known limitations

Unaudited contract. The smart contract is built on audited components but hasn't been reviewed as a whole by a professional security firm — not intended for real funds yet. Ran Slither (static analysis) on it directly: no critical or high-severity findings — flagged items were standard-severity notes already mitigated by OpenZeppelin's ReentrancyGuard, or accepted patterns like timestamp-based dispute windows.

Shared daily limit for escrow jobs. The $100/day cap for job escrow is global across all visitors — but wallet funding and P2P transfers now have a separate $6/day limit tracked per signed-in Google account.

Keeper threshold is short for demo purposes. The keeper sweep uses a 5-minute stuck threshold to make the automatic force-refund demonstrable; a production deployment would tune this much closer to the contract's own 7-day timeout.

Force-refund favors the client. If a dispute times out after 7 days, funds return to the client by design, not the worker.
